# Проверка безопасности (этап 9)

Что проверялось, чем, что нашли и что осталось. Каждый пункт «проверено» подтверждается автотестом или сквозным тестом в браузере
(см. [testing.md](testing.md)); пункты «не проверено» названы прямо.

## Что проверено и как

| Область | Проверка | Где |
|---|---|---|
| Доступ без входа | Все ~60 маршрутов магазина отвечают 401 анониму — **обход автоматически перебирает все маршруты по декораторам**, поэтому новый маршрут без защиты ловится сам | `apps/api/test/security.spec.ts` |
| Изоляция магазинов (IDOR) | Не-участник получает 404 на каждом маршруте магазина (существование магазина не раскрывается); чужие id в теле/пути — 404 | `security.spec.ts`, `catalog.spec.ts`, `orders.spec.ts`, `media.spec.ts`, `organizations.spec.ts` |
| Роли (RBAC) | Для каждого маршрута: сотрудник получает 403 **ровно** там, где его роли не хватает прав; права маршрутов сверены с `SYSTEM_ROLE_DEFINITIONS` | `security.spec.ts`, `rbac.spec.ts` |
| Повышение привилегий | Нельзя выдать права, которых нет у выдающего; системные роли неизменяемы; кастомная роль не может сойти за владельца | `rbac.spec.ts` |
| Подбор и спам | Лимит запросов на IP (429), лимит на API-ключ, не более 3 неоплаченных заказов на email | `security.spec.ts`, `api-keys.spec.ts`, `orders.spec.ts` |
| Внедрение | Текст в `q`/сортировке — только параметры запроса; сортировка по белому списку (иначе 400); `__proto__` и лишние поля отклоняются строгими схемами | `security.spec.ts`, `db.spec.ts` |
| Размер/форма запросов | Тело 3 МБ → 413; битый JSON → 400 без стека | `security.spec.ts` |
| Утечки в ошибках | Единый формат ошибок с `requestId`, без SQL, драйвера и стека | `security.spec.ts`, `app.spec.ts` |
| Заголовки | API: `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, CSP `default-src 'none'`. Сайт: `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy`. Mini App: то же, но показ во фрейме разрешён только Telegram (`frame-ancestors`) | `security.spec.ts`, `next.config.ts` |
| Платежи | Подпись вебхука Stripe по сырому телу; сумма и валюта сверяются с заказом, а не с событием; дедупликация событий; идемпотентность; оплата после отмены фиксируется, а не теряется | `billing.spec.ts`, `orders.spec.ts` |
| Деньги | Только валюты с двумя знаками (иначе Stripe списал бы в 100 раз больше); цены считает сервер, клиент присылает только варианты и количества | `money.spec.ts`, `orders.spec.ts` |
| Остатки | Резерв атомарный: 6 параллельных покупателей последней единицы → одна покупка, остаток не уходит в минус | `orders.spec.ts` |
| Загрузка файлов | Билет загрузки подписан (HMAC), привязан к магазину, ключу, типу, размеру, живёт 15 минут; после загрузки сервер проверяет реальный файл; подделка/чужой билет → 422; бакет сам ограничивает размер и тип | `media.spec.ts` |
| Telegram | Подпись `initData` проверена независимой эталонной библиотекой; подделка, повтор, просрочка, чужой бот отклоняются | `telegram.spec.ts` |
| Секреты | Токены ботов шифруются (AES-256-GCM); ключи API хранятся только хешем; в журнал не попадают поля `token/secret/password…`; секретный ключ Supabase только на сервере | `unit.spec.ts`, `api-keys.spec.ts` |
| Вход | Токен Supabase проверяется по JWKS (подпись, `iss`, `aud`, `exp`); заблокированный пользователь отклоняется сразу, хотя токен ещё действует (проверено в браузере) | `auth.spec.ts`, e2e `admin.spec.ts` |
| Перенаправления | Адрес после входа (`?next=`) — только путь внутри сайта; адреса возврата после оплаты строит сервер | `apps/web/lib/supabase.ts`, `orders.service.ts` |
| Зависимости | `pnpm audit` (все и production): известных уязвимостей нет; запускается в CI | CI |
| Браузер | Сквозные сценарии: покупка до подтверждённого заказа, регистрация/вход, кабинет бренда с загрузкой фото, админка с блокировкой, закрытые страницы без входа | `e2e/tests` |

## Найдено и исправлено

| Находка | Исправление |
|---|---|
| Валюты без копеек (JPY и др.) списывались бы в 100 раз больше | Принимаются только двузначные валюты |
| Ссылку загрузки можно было использовать для файлов любого размера/типа мимо квоты тарифа | Бакет ограничен по размеру и типу, существующий бакет обновляется |
| Дефект `slugify`: буквы с диакритикой превращались в дефисы | Исправлено, тест |
| Зарегистрированный покупатель с протухшей сессией не мог оформить заказ | Оформление повторяется как гость |
| Заголовки безопасности отсутствовали | Добавлены в API и оба сайта |

## Что осталось (осознанные ограничения и риски)

| Риск | Почему / когда |
|---|---|
| Лимиты запросов считаются **в памяти экземпляра**; на Vercel их много, защита от перебора ослаблена | Нужен Redis (этап 10) |
| На сайте нет `Content-Security-Policy` | Next использует встроенные скрипты; нужен режим nonce — отдельная задача |
| Токен просмотра заказа лежит в адресе страницы (виден в истории браузера); от утечки через Referer защищает `Referrer-Policy` | Для гостевого заказа без аккаунта иначе нельзя; вошедший покупатель открывает заказ без токена |
| Сессия Supabase хранится в cookie браузера (не `HttpOnly`) — так устроен их клиент; XSS на сайте украл бы её | Поэтому важна CSP (см. выше) и отсутствие `dangerouslySetInnerHTML` (в коде не используется) |
| Подбор пароля и спам-регистрации ограничивает Supabase, а не мы | Настройки Supabase → Authentication → Rate Limits; для запуска подключить CAPTCHA |
| Брошенные загрузки (файл есть, подтверждения нет) остаются в хранилище | Чистка по расписанию — этап 10 |
| Страница несуществующего магазина отдаёт HTTP 200 (с `noindex` и текстом «не найдено») | Особенность потоковой отдачи Next |
| Деньги за заказы идут на аккаунт Stripe платформы | Выплаты брендам не реализованы (Stripe Connect) |
| **Независимого пентеста нет** | Это самопроверка автотестами и обзором кода, она не заменяет аудит третьей стороной перед приёмом настоящих платежей |
