# REST API (этапы 5–8)

Базовый адрес: `/api/v1`. Swagger UI: `/api/docs` (JSON: `/api/docs-json`). Включается `SWAGGER_ENABLED`.
Код: [`apps/api/src`](../apps/api/src). Схемы запросов — в [`packages/shared/src/schemas.ts`](../packages/shared/src/schemas.ts)
(одни и те же Zod-схемы валидируют сервер и формы фронтенда).

## Конвейер запроса

```
ThrottlerGuard → AuthGuard → TenantGuard → PermissionsGuard → SubscriptionGuard → ZodPipe → контроллер → сервис → Prisma
                                              любое исключение → AllExceptionsFilter (единый формат)
```

| Шаг | Что делает |
|---|---|
| **ThrottlerGuard** | лимит `THROTTLE_LIMIT` запросов в минуту на IP (для всех маршрутов, включая публичные) |
| **AuthGuard** | `Authorization: Bearer <Supabase JWT>` **или** `X-API-Key`. Обе формы сразу — 400. Результат — `req.principal` |
| **TenantGuard** | организация берётся **только из `:orgId` в URL**; нужен активный участник (или SUPER_ADMIN, или ключ этой организации). Чужая/несуществующая/кривая — одинаково **404** |
| **PermissionsGuard** | проверяет `@RequirePermissions(...)` на сервере. **Маршрут без правила отклоняется (403)** — забытый декоратор не открывает эндпоинт |
| **ZodPipe** | валидация body/query; `.strict()` — лишние поля = 400 |
| **AllExceptionsFilter** | `{ statusCode, message, details?, requestId }`; без стектрейсов, SQL и текстов драйвера |

### Правила доступа маршрута (ровно одно обязательно)

| Декоратор | Кто проходит |
|---|---|
| `@Public()` | любой (health) |
| `@UserOnly()` | только вошедший пользователь; **API-ключ — 403** (свой аккаунт, создание организаций, выпуск ключей) |
| `@MemberOnly()` | пользователь — активный участник `:orgId` |
| `@RequirePermissions(a, b)` | пользователь **или** ключ, у которого есть **все** перечисленные права |

Права: каталог `PERMISSIONS` в `@repo/shared` (29 ключей, области `PLATFORM` / `ORGANIZATION`).
Платформенное право проверяется по ролям пользователя (`user_roles`), организационное — по роли в **этой** организации.
SUPER_ADMIN проходит все проверки.

## Аутентификация

**Веб (Supabase Auth).** Регистрация, подтверждение email, вход, сброс пароля выполняет Supabase на фронтенде.
API проверяет токен **сам**: подпись по JWKS проекта (`ES256/RS256/EdDSA`), `iss`, `aud`, `exp`.
`alg: none` и HS-токены отвергаются (HS256 принимается только при заданном `SUPABASE_JWT_SECRET`, для старых проектов).
Анонимные сессии Supabase не принимаются. Любая ошибка токена → один и тот же `401`.

Что происходит при первом запросе: создаётся `users` + `profiles` + `user_settings`.
Пользователь, заранее созданный с тем же **подтверждённым** email (например, сидовый SUPER_ADMIN), привязывается, а не дублируется.
Неподтверждённый email не сохраняется и не привязывается. Email, уже занятый другим аккаунтом, → 409.

**Сессии.** `session_id` из JWT фиксируется в `sessions`. Отзыв (выход на устройстве, блокировка) действует сразу,
хотя сам JWT ещё не истёк. Чужой `session_id` с токеном другого пользователя → 401.

**Блокировка** проверяется на каждом запросе (читается статус из БД): заблокированный получает 403 немедленно.

**API-ключи.** Формат `pk_<8 hex>.<43 символа>`; секрет — 256 бит из CSPRNG; в БД только SHA-256 хеш (сравнение за постоянное время),
полный ключ показывается **один раз** при создании. Права ключа ⊆ прав его создателя на момент выпуска.
Организационный ключ действует только в своей организации; личный — как владелец, но только пересечением прав ключа и **живых** прав владельца.
Лимит запросов на ключ (`rateLimitPerMinute`) → 429 + `Retry-After`. Каждый вызов (и отказанный) пишется в `api_logs` (только путь, без query).
Ключи участника отзываются, когда его удаляют из организации.

## Каталог и витрина (этап 8.1)

**Товар** — один документ (`productInputSchema`): поля, опции (до 3: `Size`, `Color`, `Fabric` — по ним витрина строит
размеры, свотчи и фильтры), варианты (цена в минорных единицах, остаток, SKU), медиа и коллекции.
`POST` создаёт, `PUT` заменяет целиком. Варианты с `id` сохраняют его (корзины и заказы остаются привязаны),
не перечисленные — удаляются (строки заказов остаются снимком). Проверки: варианты задают ровно все опции и только
существующие значения, без дублей; уникальность slug и SKU в магазине → 409.
**Любой** id в теле (медиа, коллекция, таблица размеров, вариант) обязан принадлежать этой организации, иначе 404.

**Контент витрины** (`storefrontContentSchema`) — тоже один документ: настройки (порог бесплатной доставки, плашки доверия,
способы оплаты, футер), секции главной (`hero`, `featured`, `grid`, `drop`, `collections`, `social`, у каждой `enabled`),
отзывы, плейлист, лукбук. Ссылки футера — только пути внутри магазина (`/…`), соцсети и картинки — только `https://`.

**Публичное API** отдаёт ровно модели витрины из `@repo/shared` (`StoreConfig`, `StoreCatalog`): только активный магазин,
товары `ACTIVE`, опубликованные коллекции. Без id, остатков, SKU и черновиков (наличие размера — только `inStock`).
Секции тарифа (`drop_countdown`, `music_player`, `lookbook`) скрываются, если тариф их не включает, — данные бренда сохраняются.
Сайт и Mini App читают его на сервере с кэшем Next (`'use cache'`, профиль `minutes`): правки бренда видны в течение нескольких минут.

**Медиа.** Загрузка файлов (Supabase Storage) — в кабинете бренда (8.4); пока `GET …/media` только перечисляет.
Демо-магазин использует векторную «арт»-графику (`media_files.meta`), реальные файлы отдаются по адресу публичного бакета `media`.

## Заказы и оплата (этап 8.2)

**Корзина** живёт в браузере (localStorage, по магазину) и содержит только выбор вариантов и количества. Всё, что касается денег,
считает сервер: `quote` (цены из БД, доставка, наличие) и `checkout`. Тело `checkout` строгое — цена, итог, организация в нём недопустимы.

**Checkout** (`POST /storefront/:store/checkout`, гость или `Authorization: Bearer`; неверный токен → 401, а не тихий гостевой заказ):
1. в одной транзакции для каждого варианта (в фиксированном порядке) `UPDATE … SET stock = stock - n WHERE stock >= n` — остаток
   резервируется атомарно, перепродать нельзя (параллельные покупатели последней единицы: один 201, остальные 409; плюс `CHECK stock >= 0` в БД);
2. снимок позиций (название, вариант, SKU, цена), номер заказа из `organizations.next_order_number`, платёж `PENDING (purpose=ORDER)`;
3. страница оплаты Stripe; адреса возврата строятся **на сервере** из `PUBLIC_WEB_URL` / `PUBLIC_MINI_APP_URL` (нет open redirect);
4. если страницу оплаты создать не удалось — заказ отменяется, остаток возвращается сразу.

Ответ содержит `token` — **один раз**; в БД только его SHA-256. По токену (или по входу покупателя-владельца) открывается заказ
`GET /storefront/:store/orders/:id`; любая другая попытка — 404. Эта страница при `PENDING_PAYMENT` сама опрашивает провайдера
(вебхук мог ещё не прийти) и отдаёт `payUrl`, пока платёж ещё можно завершить.

**Состояния**: `PENDING_PAYMENT → PAID → FULFILLED`, `PENDING_PAYMENT → CANCELED` (истёк/отменён, остаток возвращён), `PAID/FULFILLED → REFUNDED`
(полный возврат). Бренд закрывает только оплаченные (`fulfill`) и отменяет только неоплаченные (`cancel`); возврат денег — через платформу.

**Истечение.** Раз в 5 минут задача отменяет заказы, неоплаченные дольше 40 минут (страница Stripe живёт 30): сначала спрашивает
провайдера — платёж с потерянным вебхуком становится `PAID`, а не выбрасывается. Лимит: не более 3 неоплаченных заказов на email в магазине
(иначе можно «заморозить» весь остаток).

## Кабинет покупателя (этап 8.3)

**Вход** выполняет Supabase на сайте (`apps/web`): `/login`, `/register`, `/forgot-password`, `/reset-password`, `/auth/callback` (ссылка из письма).
Токен Supabase браузер отправляет в API как `Authorization: Bearer`; API проверяет его само (см. «Аутентификация»).
Пароль ≥ 8 символов; ответ «проверьте почту» одинаков для существующего и нового адреса (аккаунты не раскрываются).
Адрес после входа (`?next=`) принимается только как путь внутри сайта.

**Мои заказы.** `GET /users/me/orders` — только заказы этого пользователя (по всем магазинам). `POST /users/me/orders/claim` привязывает
гостевые заказы, оформленные с **подтверждённым** email аккаунта (чужие и уже привязанные не трогает; у Telegram-пользователей email нет — привязывать нечего).
Заказ владельца открывается без токена из ссылки.

**Вишлист.** Гость хранит его в браузере; вошедший — на аккаунте (`wishlist_items`, до 200 товаров на магазин, только активные товары
этого магазина). При входе локальный список переносится на аккаунт.

**Кабинет** `/account`: заказы, профиль, привязка/отвязка Telegram, устройства (сессии) и выход с них, удаление аккаунта.

## Кабинет бренда (этап 8.4)

Интерфейс `/dashboard` (сайт `apps/web`): магазины пользователя и создание нового; внутри магазина — обзор (заказы, тариф, использование),
товары (опции, варианты с ценой/остатком/SKU, фото, коллекции, размерная сетка), коллекции, размерные сетки, медиатека, заказы
(«выполнен», «отменить» неоплаченный), контент витрины (баннер, подборки, отсчёт, плеер, лукбук, отзывы, футер, доставка), команда
(роли, приглашения со ссылкой `/invite?token=…`), тариф и оплата, настройки (название, свой Telegram-бот, API-ключи).
Все данные идут через уже описанное API; права и изоляция магазинов проверяются сервером, интерфейс только показывает ответы.

**Загрузка файлов без прохода через API** (Supabase Storage, публичный бакет `media`):
1. `POST …/media/upload-url` — проверка типа (JPEG/PNG/WebP/AVIF/GIF до 8 МБ; MP3/M4A/OGG/WAV до 20 МБ, звук — только на тарифе с плеером),
   лимита `storage.mb` тарифа → одноразовый токен загрузки и подписанный **билет** (HMAC на `JWT_SECRET`, 15 минут, привязан к магазину, ключу, типу и размеру);
2. браузер загружает файл прямо в хранилище по токену;
3. `POST …/media {ticket}` — сервер проверяет подпись билета и что файл **действительно лежит** в хранилище с заявленным размером и типом (иначе файл удаляется),
   и только потом записывает его. Повторное подтверждение безвредно; чужой, подделанный или просроченный билет → 422.
Удалить можно только файл, который нигде не используется (иначе 409). Нужен ключ `SUPABASE_SERVICE_ROLE_KEY` **только на сервере API** (без него — 503).

## Админка платформы (этап 8.5)

Интерфейс `/admin` (сайт): доступен пользователю с платформенными правами; пункты меню показываются по его правам, а **каждый вызов всё равно проверяется сервером**.
Разделы: обзор (статистика), пользователи (поиск, карточка, блокировка/разблокировка, платформенные роли), магазины (приостановить/включить,
выдать тариф на N дней), тарифы (создание/редактирование цен и функций), подписки (завершить, запустить задачу истечения), платежи (фильтр, полный или частичный возврат),
журнал действий (фильтр по началу названия), API-ключи (отзыв любого), настройки платформы (ключ–значение, JSON).

**Первый администратор.** В `.env` задайте `SEED_SUPER_ADMIN_EMAIL=вы@почта`, выполните `pnpm --filter @repo/api db:seed` (создаёт/находит пользователя и выдаёт SUPER_ADMIN),
затем зарегистрируйтесь или войдите на сайте с этим же подтверждённым email — аккаунт привяжется к заготовке. Дальше роли выдаются в `/admin/users`.

## Защита от повышения привилегий

- Выдать можно только те права, которые есть у самого выдающего (роли, ключи, назначения). SUPER_ADMIN — без ограничений.
- Системные роли неизменяемы; ключи `SUPER_ADMIN`, `ORG_*`, `PLATFORM_*` зарезервированы. Кастомная роль не может сойти за владельца:
  в проверках её ключ получает префикс `custom:`.
- Роль организации — только системная или этой же организации (проверяет и сервис, и триггер БД).
- Роль нельзя удалить, пока она назначена или есть действующие приглашения (409 с числом зависимостей).
- Нельзя удалить/понизить последнего владельца организации и убрать последнего SUPER_ADMIN.
- Модерация: нельзя заблокировать себя, SUPER_ADMIN (кроме как SUPER_ADMIN) и пользователя с большими правами.

## Журнал действий

Таблица `audit_logs`: кто (пользователь или ключ), что, над чем, IP, user-agent, метаданные.
Из метаданных вырезаются поля с именами `token|secret|password|authorization|api_key|hash`.
Запись идёт в одной транзакции с изменением. Пользователь видит свою историю (`/users/me/activity`),
админ — всю (`/admin/audit-logs`).

## Известные ограничения (осознанные)

| Что | Почему / когда исправим |
|---|---|
| Лимиты запросов и счётчики ключей **в памяти процесса** | при нескольких инстансах лимит «на инстанс»; Redis — этап 10 |
| Письма (приглашения) не отправляются: токен приглашения возвращается создателю один раз | нет почтового провайдера; подключается позже |
| Удаление аккаунта не удаляет запись в Supabase Auth | нужен service-role ключ; вход всё равно закрыт — пользователь `DELETED` |
| Корзина не хранится на сервере и не переносится между устройствами | осознанно: цены и наличие всё равно проверяются сервером; серверная корзина нужна только для синхронизации между устройствами |
| Письма покупателю (подтверждение заказа) не отправляются | нет почтового провайдера; страница заказа и email Stripe — пока единственные уведомления |
| Брошенные загрузки (файл в хранилище без подтверждения) остаются в бакете | чистка по расписанию — этап 10 |
| Письма-приглашения не отправляются | ссылка показывается приглашающему один раз и передаётся вручную |
| Кэш витрины сбрасывается по времени (минуты), а не сразу после правки | мгновенный сброс (`revalidateTag` по вебхуку) — когда появится кабинет |
| Личный API-ключ не заходит в организации | осознанно: организационные интеграции делаются организационными ключами |

## Тесты

`pnpm --filter @repo/api test` — без БД выполняются unit-тесты (проверка JWT, лимитер, пагинация, список маршрутов).
С `TEST_DATABASE_URL` (база `*_test`) запускаются интеграционные: аутентификация, RBAC, изоляция организаций (IDOR),
приглашения, API-ключи, ограничения БД — 100+ проверок на реальном PostgreSQL.
