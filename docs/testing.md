# Тестирование (этап 9)

Три слоя. Каждый ловит свое; ни один не заменяет другие.

| Слой | Что это | Где | Как запустить | Что нужно |
|---|---|---|---|---|
| Модульные | чистые функции: проверка JWT, подпись Telegram, пагинация, деньги, подбор размера | `apps/api/test/unit.spec.ts`, `packages/shared/src/*.spec.ts` | `pnpm test` | ничего |
| API-интеграционные | настоящее приложение NestJS + настоящий PostgreSQL: права, изоляция магазинов, заказы, платежи (Stripe SDK с подменёнными сетевыми вызовами), загрузки (подменённое хранилище), Telegram | `apps/api/test/*.spec.ts` (≈220 тестов) | `pnpm test` | `TEST_DATABASE_URL` на базу `*_test` (локальный Postgres) |
| Сквозные (браузер) | настоящий сайт в Edge/Chromium ходит в настоящий API и отдельную базу; вход и хранилище Supabase и Stripe — локальные заглушки | `e2e/tests/*.spec.ts` | `pnpm --filter @repo/e2e e2e` | локальный Postgres, Edge (есть в Windows) |

Плюс статические проверки: `pnpm -r typecheck`, `pnpm lint`, `pnpm audit`.

## Сквозные тесты: как устроены

```
Playwright (Edge) ──► сайт (next dev, :3100) ──► API (:4100) ──► Postgres platform_e2e
                          │                         │
                          └──► fake Supabase (:54399, вход + хранилище) ◄──┘
                                       fake Stripe (:54398) ◄── API
```

* **Ничто не касается настоящих сервисов.** Окружение API и сайта задаётся явно (`e2e/support/env.mjs`): каждая переменная выставлена
  (пустая = «не задана»), поэтому значения из вашего настоящего `.env` (живой Supabase, токен бота) не просачиваются. Подготовка базы отказывается работать
  с не-локальным хостом.
* **Отдельная база** `platform_e2e` на том же локальном Postgres: при каждом запуске `app` пересоздаётся настоящими миграциями и сидом (включая демо-магазин `ashen`
  и администратора `admin@e2e.test`).
* **Заглушка Supabase** (`e2e/support/fake-services.mjs`) выдаёт настоящие JWT (ES256) и их JWKS, поэтому API проверяет их **теми же проверками, что в бою**
  (подпись, `iss`, `aud`, `exp`). Регистрация подтверждается сразу. Хранилище принимает подписанную загрузку и отдаёт файл.
* **Заглушка Stripe**: Stripe SDK направлен на неё через `STRIPE_API_BASE_URL` (запрещено при `NODE_ENV=production`). «Оплату» тест выполняет так же, как Stripe в жизни:
  отдаёт API **корректно подписанное** событие `checkout.session.completed` (подпись создаёт официальный помощник Stripe SDK).
* Тесты проходят пользовательские пути через интерфейс: покупатель → корзина → форма → страница оплаты → подтверждённый заказ; регистрация/вход/выход;
  вишлист между сессиями; бренд создаёт магазин, товар с фото (загрузка в хранилище), получает заказ и выполняет его; администратор блокирует пользователя
  (тот сразу теряет доступ) и создаёт тариф; закрытые страницы без входа; чужой кабинет недоступен.

## Что сквозные тесты НЕ доказывают

* Настоящий Stripe, настоящий Supabase (письма, ограничения, политика паролей) и настоящий Telegram — это заглушки; живая проверка делается вручную по [deploy-vercel.md](deploy-vercel.md).
* Внешний вид и адаптивность: тесты проверяют поведение и тексты, не пиксели.
* Нагрузка: объём (сотни одновременных покупателей) не проверялся.

## Запуск

```powershell
pnpm install
pnpm test                                  # модульные + API (нужен TEST_DATABASE_URL)
pnpm --filter @repo/e2e e2e                # сквозные (создаёт platform_e2e, поднимает 3 сервера сам)
pnpm --filter @repo/e2e e2e:headed         # то же с видимым браузером
```

Перед сквозным запуском остановите свой `next dev` в `apps/web` (два `next dev` в одной папке конфликтуют). Отчёт: `e2e/playwright-report` (`pnpm exec playwright show-report`).

## Автозапуск (GitHub Actions)

`.github/workflows/ci.yml`: на каждый пуш и pull request — типы, линтер, все тесты на Postgres, сборка обоих сайтов, `pnpm audit --prod`; затем сквозные тесты в Chromium.
Отчёт Playwright сохраняется при падении.
